## Description

Replace the legacy off-chain mutations (`updateSubscriptionPlan`, `tokenAccess` field on `updateChannelInformation`) currently used by `elacity-creator` and `elacity-market` with the correct on-chain calls — `SubscriptionModule.bulkUpdatePlans(...)` and `SubscriptionModule.configureTokenOwnershipAccess(...)` — so that subscription plans and token-gating rules are actually written to the channel contract on Base. Add IPFS-pinned plan metadata (label + description + image) so the off-chain Elacity index can stay in sync with on-chain state.

This task closes the architectural gap surfaced by Irzhy on 2026-05-04:

> The off-chain part is only for direct API-change (should be deprecated now). Better to only rely on on-chain transaction.
> - For token gating, no change comparing to previous version
> - For subscription/plan management, only 1 entrypoint `bulkUpdatePlans`, can find implementation in [`elacity-web/src/lib/drm/channel/subscription.ts`](https://github.com/Elacity/elacity-web/blob/base-network-updates/src/lib/drm/channel/subscription.ts) — it is already aligned with smart contract changes.
> - For plans (add or update), we can accept a new IPFS CID for the metadata related to that plan (this will ensure we can sync the details into the database). On-chain data are only focusing on duration and price; metadata (off-chain) are more related labels and description.

## Background

### Architecture (correct)

Channel contracts on Base implement a `SubscriptionModule` with:

```solidity
struct PlanUpdate {
  uint8  actionType;  // 0=ADD, 1=UPDATE, 2=REMOVE (verify enum order against contract)
  bytes  args;        // ABI-encoded payload, see per-action shape below
}

function bulkUpdatePlans(PlanUpdate[] updates) external;

struct TokenAccessConfig {
  address tokenAddress;
  uint256 threshold;  // base units (apply ERC-20 decimals before encoding)
}

function configureTokenOwnershipAccess(TokenAccessConfig[] thresholds) external;

function getPlans() view returns (
  tuple(uint8 planId, address payToken, uint256 price, uint256 duration, bool active)[]
);

function tokenURI(uint256 planId) view returns (string);
```

Per-action `args` encodings (per Irzhy's reference):

- **ADD**:    `(address payToken, uint256 price, uint256 duration, string planURI)`
- **UPDATE**: `(uint8 planId, address payToken, uint256 price, uint256 duration, string planURI)`
- **REMOVE**: `(uint8 planId)`

`planURI` is `ipfs://<CID>` pointing to a JSON metadata blob:

```json
{
  "version": 1,
  "schema": "elacity.subscription-plan/v1",
  "name": "<label>",
  "description": "<description>",
  "image": "<inherited from channel tokenURI(0).image>",
  "properties": { "creator": "0x..." },
  "attributes": [
    { "trait_type": "Duration", "value": <duration_seconds>, "display_type": "number" }
  ]
}
```

The Elacity backend indexer reads `getPlans()` + `tokenURI(planId)` after each on-chain change and updates its database. Once on-chain works, `Channel.plans[]` and `Channel.tokenAccess[]` returned by GraphQL will reflect reality — no separate off-chain mutation needed.

### What our code does today (wrong)

`pc2-node/data/test-apps/elacity-market/wallet.js`:

```javascript
// Lines 1496–1505
// V3 contracts do not implement bulkUpdatePlans, configureTokenOwnershipAccess
// on-chain. Plan/token-gate management is handled via local catalog API.

function bulkUpdatePlans() {
  return Promise.reject(new Error('bulkUpdatePlans is not available in V3 contracts. Use local catalog API.'));
}

function configureTokenAccess() {
  return Promise.reject(new Error('configureTokenOwnershipAccess is not available in V3 contracts. Use local catalog API.'));
}
```

`elacity-market/api.js` line 1642+ falls back to `updateSubscriptionPlanLocal(...)` — local catalog only.

`elacity-creator/app.js` `saveTokenGates(...)` posts a GraphQL `updateChannelInformation { tokenAccess }` mutation. Per Irzhy: deprecated.

Both of these stubs are based on an **incorrect assumption** that V3 channel contracts don't implement these methods on-chain. They do.

### Current ABI mismatch

Both `elacity-market/wallet.js` and `elacity-creator/app.js` declare:

```javascript
'function bulkUpdatePlans(tuple(string action, bytes args)[] updates)'
```

The actual contract uses `uint8 actionType`, not `string action`. **Verify against deployed `SubscriptionModule` ABI on Base before encoding any tx**. Likely sources of truth:

1. `elacity-web` repo, branch `base-network-updates`, file `src/lib/drm/channel/subscription.ts` and adjacent `abis/SubscriptionModule.json`
2. Block explorer (Basescan) on a known Elacity channel — read the verified contract source

## Requirements

### Functional

1. **Plan ADD** — when a creator adds a plan via Creator or Market, build the metadata JSON, pin to IPFS (local + Elacity gateway mirror), encode the ADD action with `planURI = ipfs://<CID>`, and submit `bulkUpdatePlans([(ADD, encodedArgs)])` to the channel contract.
2. **Plan UPDATE** — same as ADD but with `planId`. Must merge new label/description with existing metadata fetched from `tokenURI(planId)` so partial edits don't drop fields.
3. **Plan REMOVE** — encode `(planId)` only and submit `bulkUpdatePlans([(REMOVE, encodedArgs)])`. No metadata work.
4. **Token-gate set** — encode `[(tokenAddress, threshold)]` (threshold in base units via `ethers.parseUnits(value, decimals)`) and submit `configureTokenOwnershipAccess(thresholds)`.
5. **Multi-action batches** — UI today sends one action at a time, but the contract accepts arrays. Keep the wrapper signature `bulkUpdatePlans(updates: PlanUpdate[])` so we can batch later without API churn.
6. **Wallet routing** — must work for both EOA (direct `signer.sendTransaction(...)`) and Smart Account (`Wallet.parentExecuteSmartAccountBatch(BASE_CHAIN_ID, [{to: channelAddr, data}])`), mirroring the existing `subscribeChannel`/`mintAsset` pattern.
7. **State refresh** — on tx confirmation, re-fetch the channel via GraphQL `retrieveChannelFromBackend(...)` (or directly read `getPlans()` + `tokenURI(planId)` if the indexer hasn't caught up yet) and re-render the management UI.
8. **Status UX** — every modal (`Add Plan`, `Edit Plan`, `Token Gate`) must surface the multi-step progress: `Uploading metadata to IPFS… → Awaiting wallet signature… → Confirming on-chain (block N)… → Indexer catching up… → Saved.`
9. **Remove the deprecation banners** added in v1.2.7.7 once on-chain flow is live.

### Non-Functional

10. **No breaking changes to `getPlans` reads** — the read-side already uses the contract directly and is correct.
11. **Auth requirements stay the same** — these are user-signed on-chain txs, no SIWE bearer required for the tx itself; SIWE is still needed to refresh the off-chain channel cache after the tx confirms.
12. **No regressions to `subscribeChannel`** — that path also uses `SUBSCRIPTION_MODULE_ABI`. ABI changes for `bulkUpdatePlans` must not break the `subscribePlan` encoding.
13. **Belt-and-braces IPFS pinning** — re-use the v1.2.7.7 helper (`uploadDataUrlToIpfs` in Creator, `uploadToIpfs` in Market) so metadata is pinned both locally on PC2 and mirrored to Elacity's public gateway. Falls back gracefully if either side fails.

## Acceptance Criteria

1. Adding/updating/removing a subscription plan in either Creator or Market sends a real `bulkUpdatePlans` transaction visible on Basescan with correctly encoded args.
2. The plan's `tokenURI(planId)` resolves to an IPFS CID containing the label, description, duration, and inherited channel image.
3. After indexer sync (≤ 5 min), the same plan appears on production Elacity Web and in our `retrieveChannelFromBackend` response with matching label/description/price/duration.
4. Setting a token-gate sends a real `configureTokenOwnershipAccess` transaction; `checkChannelAccess` returns correct `haveAccess` based on holder balance.
5. Both EOA and Smart Account flows work end-to-end.
6. The v1.2.7.7 deprecation banners are removed from all three modals + two manage sections.
7. No regressions on `subscribeChannel`, `getPlans`, `mintAsset`, or any other existing wallet flow.
8. Error states (user rejects sig, tx reverts, IPFS pin fails) are surfaced with actionable messages and a "Try again" affordance — no silent failures.
9. The duplicated `SUBSCRIPTION_MODULE_ABI` declarations are consolidated into one shared module.

## Testing Strategy

### Pre-flight: ABI verification

Before touching any UI code:
1. Pull `SubscriptionModule.json` from elacity-web (branch `base-network-updates`)
2. Read source on Basescan for one known channel contract on Base
3. Diff against our current ABI string; document the corrected fragments
4. Smoke-test encoding by manually building a fake ADD payload and calling `eth_call` (read-only simulate) against a deployed channel via `Wallet.getProvider().request(...)` — this catches encoder mismatches before signing.

### Per-flow contract fixtures

Capture working request/response fixtures from elacity-web for:
- ADD plan (note the `planId` returned in event logs)
- UPDATE plan (verify metadata merge)
- REMOVE plan (verify subsequent `getPlans()` state)
- Set 1 token-gate (ERC-20)
- Set 1 token-gate (ERC-721)
- Set 0 token-gates (clear all)

Replay against our Creator/Market and assert byte-for-byte tx data equality.

### Wallet matrix

Each scenario × {EOA, Smart Account} × {Creator app, Market app} = 24 manual passes. Spot-check 6 of these end-to-end on a test channel.

### Indexer race

Verify the optimistic-merge + polling path:
- Add plan → confirm tx → see plan in UI immediately (optimistic)
- Wait for indexer (~30 s) → swap to indexed data → verify identical
- Reload page → still see plan (indexed)
- Edge: fast page reload during the polling window should not duplicate or drop the plan.

## Notes

- **Irzhy's IPFS-CID requirement is the new piece**, on top of his earlier guidance. We hadn't planned for it; the implementation now needs IPFS pinning *inside* the plan-write path. Keep this synchronous (await pin → submit tx) so the planURI is in the tx data — don't post-pin.
- **Mask plan IDs?** elacity-web's TS uses a `maskedPlanId(planId)` helper for some calls. Verify whether `tokenURI(planId)` expects raw or masked. If masked: replicate the helper.
- **Backwards-compat with off-chain plans**: Channels created before v1.2.7.8 may have plans only in the off-chain catalog (no on-chain plan). On the read side, prefer on-chain `getPlans()` truth; if a UI shows an off-chain-only plan and a creator tries to edit it, treat it as ADD (not UPDATE) on first save. Document this clearly.
- **Token-gate decimals storage**: backend already stores `decimals` per gate (we fixed this in v1.2.7.7). The on-chain call only needs `(address, threshold-in-base-units)`. Decimals are a UI concern only — keep them in the off-chain mirror so the UI can render `value × 10^-decimals` correctly.
- **No new GraphQL mutations** — this task removes our use of `updateSubscriptionPlan`. The off-chain `updateChannelInformation { name, description, image, coverImage, categories }` remains valid (it covers fields with no on-chain representation).
- **Coordinate with Irzhy** — confirm the exact `PlanActionType` enum values and the `tokenURI(planId)` semantics (raw vs masked) before encoding the first tx. A 30-min sync would close the riskiest unknowns.

## Out of Scope

- Multi-currency (non-USDC) plan payments — handled implicitly via `payToken` in args, but UI currency selection is left as v1.2.8+.
- Recurring vs. one-time subscription toggle in the management UI (the `subscribePlan(uint8 planId, bool recurring)` arg is set by the subscriber, not the creator).
- Migration of existing off-chain-only plans to on-chain (one-time backfill) — separate task if needed.
- Gasless plan management via meta-tx — not requested.
