Six waves of security work shipped. v1.2 is code-complete; the only release-blockers are non-engineering (RG3 smoke matrix needs the founder's session token, RG5 needs Irzhy's contract update, RG6 needs the supernode-cut decision). We have **calendar slack and compute slack** before tag.

This document is the answer to: *"what do we ship next that converts security correctness into adoption — for individuals AND enterprise — and that pulls the four-layer ElastOS thesis closer to inevitable?"*

It's a ranked plan, not a wishlist. Each item maps to:
- **Layer** (L1 Runtime / L2 Capsule SDK / L3 dDRM Protocol / L4 PC2)

- **Audience** (Creators / Devs / Users / Enterprise)
- **Effort** (S = days, M = ~1 eng-week, L = multi-week)
- **Bible commandment** it primarily serves

If an item doesn't appear here, it's a distraction (Bible §III, "the woman in the red dress").

## Pre-v1.2 work — what we can ship NOW without invalidating release gates

These items are **purely additive**: they don't touch any code path covered by RG3 or RG4 (`npm run test:security`, 79 cases). They can land on `feature/lit-chipotle-migration` ahead of the v1.2.0 tag, or in `v1.2.0-rc` patches, without re-running the security smoke matrix from scratch.

Ranked by leverage:

### P0 — Telemetry plumbing for the four metrics that matter

> Bible §VIII (the only metrics that matter): WAC, time-to-first-value, deploy frequency, change-failure rate.

**What:** Add `POST /api/telemetry/onramp` (PC2 node) + a single CSV/JSON dashboard rendered on a supernode at `dash.ela.city/onramp`. Events: `install_started → wallet_ready → first_capsule_open → first_payment`. Privacy-preserving — only counts and rough timestamps, no per-user tracking unless the user opts in.

**Why now:** Every other Tier-1 item below claims a metric. Without the pipe, the claims are theatre. **DoD #5** (Bible): *"if you can't name the metric this PR moves, you don't understand why you're shipping it."* This is the metric infrastructure.

**Effort:** S (~3 days). Endpoint + Postgres/SQLite table on supernode + a 100-line static dashboard.

**Risk to v1.2:** None. New endpoint, no existing surface touched. Auth = `requireOwner` on the WRITE side, public on the READ side (counts only).

### P1 — App bundle packager + IPFS pin script (unblocks the dapp store, see §"First Capsules" below)

**What:** A standalone Node script `pc2-node/scripts/package-app.ts <app-name>` that:
1. Tarballs `pc2-node/data/test-apps/<name>/` → `<name>-<version>.tar.gz`
2. Computes SHA-256 + Ed25519 signature using a dev signing key
3. Pushes to IPFS via the existing Helia stack
4. Emits a registry entry JSON to stdout (signed `distribution` block)

**Why now:** The supernode registry already serves a catalog. The app install pipeline already accepts `(manifest, cid)`. The only missing pieces are (a) the packager, (b) `extractBundle` tar.gz support, (c) registry entries with real CIDs. Doing this pre-v1.2 means **the dapp store ships in v1.2.1 without any node-code change** — only a registry update. (See §"First Capsules" below for the full picture.)

**Effort:** S (~2 days). Reuses existing IPFS + signing primitives.

**Risk to v1.2:** None. Standalone script, never run by the node at runtime. Tarball extraction support in `extractBundle` is a 20-LOC additive change behind a try/catch — falls back to today's behaviour on any error.

### P2 — `npx create-elacity-capsule <template>` scaffold

> Bible §II.4 (Volume) and §VI (Acquire). The 10-minute promise lives or dies in the first `git clone`.

**What:** A separate npm package `@elacity/create-capsule`. Templates: `storefront`, `gated-content`, `agent-app`, `nft-drop`. Each template ships a working `app.json`, `index.html` skeleton, wallet-bridge wiring, and a 10-line README. Run `npx @elacity/create-capsule my-capsule --template storefront` and you have a deployable capsule directory.

**Why now:** Sash can write the templates while RG3 is being run. Doesn't touch the PC2 node at all — it's a separate npm publish.

**Effort:** M (~1 eng-week, but parallel-able with other work).

**Risk to v1.2:** Zero. Independent package.

### P3 — Installer hardening pass (the existing one-liners get teeth)

**What:** We already have working one-line installers — `pc2-node/scripts/install.sh` (served at `https://ela.city/install.sh`), `scripts/install-pc2.sh` (served at `https://elastos.pc2.net/install.sh`), plus `install-wsl.sh` and `install-arm.sh` for the platform variants. They're documented at docs.ela.city/install. What they're missing for the "10-minute promise" Bible commitment:

1. **SHA-256 + Ed25519 signature pinning of the downloaded artifact.** Right now both scripts pull `ghcr.io/elacity/pc2-node:latest` — a mutable tag with no out-of-band signature verification. Same pattern A7 just shipped for the ollama binary fetch.
2. **Auto Let's Encrypt cert against `<random>.pc2.ela.city`.** DDNS endpoint runs on the supernode so users don't have to BYO domain. End-to-end: paste the curl line on a fresh box → working PC2 with TLS in <10 min.
3. **Cloud-provider one-liners for Hetzner / Vultr / OVH / Lightsail / DigitalOcean.** A non-technical user can paste *one* line into the cloud-console "user data" / "cloud-init" field at provisioning time.

**Why now:** scope is much smaller than rebuilding from scratch — most of the work is supernode-side (DDNS endpoint + signature publishing). PC2-node-side change is a 30-LOC verification block in the installer scripts.

**Effort:** S (~2–3 days total, mostly supernode work).

**Risk to v1.2:** Zero (off-binary, the verification block is additive in the installer shell scripts, never run by the node at runtime).

### P4 — Compliance pack drafts (start the legal clock)

**What:** GDPR DPA template, SOC2 readiness statement, "non-custodial infrastructure" legal opinion (one lawyer engagement), insurance attestation. Single PDF zip behind `enterprise.ela.city/compliance`.

**Why now:** Lawyer turnaround is weeks. Start now → ready for the first enterprise design partner conversation in 4–6 weeks. Founder-time only; no engineering capacity needed.

**Effort:** S in eng-time (zero); M in elapsed time (lawyer fee + revisions).

**Risk to v1.2:** Zero (off-codebase).

## First Capsules on ElastOS — the dapp store unlock

> "Could Glide / Elacity NFT / Market / Creator / Player / Viewer be downloaded from the dapp store instead of pre-installed? They're almost the first dapp capsules on ElastOS."

**Yes, and the answer is closer than you'd guess.** This section is the analysis + the path.

### What's already shipped (the 80%)

| Component | Location | Status |
|---|---|---|
| Manifest schema with `distribution.{cid,signature,signedBy,channel,updateUrl,size}` | [`AppInstallService.ts`](../../pc2-node/src/services/AppInstallService.ts) `AppManifest` interface | ✅ Implemented |
| `install(manifest, cid)` — fetches from IPFS, validates, extracts, registers | [`AppInstallService.ts:181-250`](../../pc2-node/src/services/AppInstallService.ts) | ✅ Implemented |
| Ed25519 signature verification (warn-only in v1, enforced in v2) | [`AppInstallService.ts:261-300`](../../pc2-node/src/services/AppInstallService.ts) | ✅ Implemented (warn-only); enforcement tracked under [SEC-2026-04-22-WAVE7-POLISH](../../.cursor/tasks/SEC-2026-04-22-WAVE7-POLISH/SEC-2026-04-22-WAVE7-POLISH.md) (A15 capsule-signing v2 cutover) |

| Capability scopes (`CAPABILITY_SCOPES`) — 1:1 mapping to Runtime token actions | `pc2-node/src/types/capabilities.ts` | ✅ Forward-compatible |

### What's missing (the 20%)

1. **Tar.gz extraction in `extractBundle`** — currently only handles single-file HTML. Falls back to "write as-is" with a warning. **Fix:** add `tar` (Node built-in via `node:zlib` + `tar-stream`), ~20 LOC. Tracked as §P1 item P1a.
2. **Bundle packager script** — tarball + sign + IPFS-pin + emit registry entry. ~80 LOC standalone. Tracked as §P1 item P1b.
3. **Registry entries with real CIDs + signatures** — supernode-side data update. Zero code change once §P1 ships. Scope split below.
4. **Frontend "Install" button** — needs a wrapper UI on top of `apps.ela.city`. Tracked as §T1.1.
5. **Elacity Labs Ed25519 dev signing key + public-key-of-record published at `apps.ela.city/signing-key.json`** — operational task, ~30 minutes including key generation and HSM seal.
6. **Supernode pin set** — InterServer + Contabo supernodes pin every CID they advertise in the registry. Tiny daily cron (~30 LOC). See "How capsule content is hosted" below.

### How capsule content is hosted (the four-source model)

Today the supernodes serve **registry metadata**, not capsule bytes. Capsule bytes live on IPFS. For the v1.2.1 dapp-store launch we want **four independent sources** for every capsule, ranked by DHT-fetch priority:

| Source | Status | Role |
|---|---|---|
| `ipfs.ela.city` (canonical Elacity Kubo node) | ✅ Live today, used as fallback gateway by PC2 + bootstrap multiaddr | Primary host. Already pins all Creator-uploaded media + NFT artwork. Pinning the 6 capsule tarballs here is a 1-command operational task. |
| **InterServer supernode pin set** | 📋 Half-day op-task | Daily cron reads its own registry, runs `ipfs pin add <cid>` for every advertised CID. Becomes the second guaranteed seeder. |
| **Contabo supernode pin set** | 📋 Half-day op-task | Same as InterServer. Becomes the third guaranteed seeder. |
| Any PC2 that has installed the capsule | ✅ Live today via `ContentSeedingService` | Every successful install + auto-pin adds another seeder organically. The network strengthens with adoption. |

**Why this matters for v1.2.1:** removes single-host dependency on `ipfs.ela.city`. If any one source is down, the other three still serve the same content-addressed bytes. Fresh PC2 installs are never DHT-gambled — there's always at least one supernode pinning what the supernode itself advertises. Same fragility-fix pattern we used for the registry mesh-sync.

**Operational ownership:** belongs to the supernode operators (same hands that wired `ipfs.ela.city`). No PC2-node code change, no protocol change. Tracked as item §P1.6 above.

**Convergence note:** in Runtime v2, this pattern generalises — every federated dapp registry should pin what it advertises. Anders' Runtime can adopt the same `pin-what-you-list` rule when third-party dapp registries appear.

### Default apps vs dapp-store capsules — the split for v1.2.x

> Founder direction (2026-04-23): the dapp-store unlock should target **two apps** at v1.2.1 launch, not all six. The four protocol apps stay bundled.

**Default / bundled apps** — ship inside the PC2 binary, can't be uninstalled, signed but installed-by-default:

| App | Why bundled |
|---|---|
| `elacity-market` | This *is* the Elacity marketplace surface. Removing it would break the protocol's UX promise. |
| `elacity-creator` | Companion to Market. Without it, no creator can mint. The "creator" half of the loop. |
| `elacity-player` | Runtime media player — opens any `.ddrm` video/audio. Protocol surface, not a "dapp." |
| `ddrm-viewer` | Runtime universal viewer — opens any `.ddrm` non-media (PDF, 3D, fonts, archives, etc). Protocol surface. |

These four are **still signed and still listed in the registry** (so their version + signature is verifiable, and they receive update-on-consent prompts), but they are not removable from the start menu and don't require a dapp-store install flow. Think of them as the equivalent of `Photos.app` or `Mail.app` on macOS — system apps that happen to be open-source and signed.

**First dapp-store capsules** — downloadable from `apps.ela.city`, can be installed/uninstalled by the user, ship as the proof points for the dapp-store mechanic:

| App | Why dapp-store capsule |
|---|---|
| `elastos-nft` | Galaxy NFT marketplace. Optional surface — not every PC2 user wants NFTs. Perfect first removable dapp. |
| `glide-finance` | Glide DEX (Uniswap V2 fork on ESC). Optional surface — not every PC2 user wants a DEX. Perfect first removable dapp. |

**Why this split is the right v1.2.x scope:**

- **Risk-bounded:** the four protocol apps are unaffected by any dapp-store regression. If the install flow has a bug, NFT or Glide users can fall back to the bundled (uninstalled) state with one click; Market/Creator users see no change at all.
- **Two real proof points:** "PC2 fetched, verified, sandboxed, and ran a third-party dApp" is true after one successful Glide install. We don't need 6 apps to demonstrate the model.
- **Optionality maps to user intent:** users who don't want a DEX shouldn't have one in their start menu. Users who don't want an NFT marketplace shouldn't have one. Bundled-by-default for these is a UX liability, not an asset.
- **Convergence story unchanged:** in Runtime v2, all six apps still become capsules. The bundled/downloadable distinction is a v1.2.x install-experience choice, not an architectural one. (See "Anders' Runtime alignment" below.)

### The migration path (no breaking change for v1.2 users)

```
Phase 0 (today):
  All 6 apps live in data/test-apps/ → installed via installFromLocal at startup
  Registry serves a catalog with ONLY metadata (no .cid)

Phase 1 (v1.2.0 + 1 week, ships pre-tag):
  Add tar.gz extraction + packager script (§P1)
  Generate Elacity Labs Ed25519 signing key
  Sign + pin all 6 apps to IPFS (uniform — bundled and dapp-store
    capsules both need a CID + signature for update verification)
  Update registry entries with .cid + .signature + .signedBy
  Mark Market/Creator/Player/Viewer with "role": "system"
  Mark NFT/Glide with "role": "dapp"
  PC2 node still prefers bundled version on startup (zero behaviour change)

Phase 2 (v1.2.1 — dapp store launches with NFT + Glide as first capsules):

## Paid Capsules — when the dapp store IS the marketplace

Free capsule install is the Phase 1 unlock. The compounding lever is **paid capsule install**, where the same dDRM protocol that today wraps a video, PDF, or AI model wraps the `.tar.gz` of a capsule.

The protocol does not care what's inside the encrypted bytes. A signed-and-encrypted tarball is a signed-and-encrypted tarball. So:

- **Free capsule** = signed tarball, IPFS-pinned, anyone can install
- **Paid capsule** = encrypted+signed tarball, IPFS-pinned, install gated by an on-chain ACCESS_TOKEN

Same UX. Same wallet flow. Same royalty mechanics. **Same contracts already deployed on Base mainnet.**

### Phase 3 mechanics (extends the migration plan above)

```
Creator (extended Elacity Creator app):
   1. tar czf my-capsule-1.0.0.tar.gz my-capsule/
   2. Generate random 32-byte CEK (Content Encryption Key)
   3. Encrypt tarball with AES-256-GCM(CEK)              → encrypted blob
   4. Wrap CEK in Lit/Chipotle TEE with PKP              → encrypted CEK
   5. Pin encrypted blob to IPFS                          → CID
   6. Mint ACCESS_TOKEN on Base via existing dDRM contracts:
        - capsuleId      = sha256(manifest)
        - price          = N ELA
        - royaltyBps     = 1000 (10% on resale)
        - resaleAllowed  = true
   7. Submit registry entry with distribution.drm = true + dDRM metadata

Buyer:
   1. Browses apps.ela.city, sees "Install for N ELA" button
   2. Click → wallet popup → buys ACCESS_TOKEN on Base
   3. PC2 fetches encrypted blob from CID
   4. PC2 → Lit/Chipotle: "0xBuyer has ACCESS_TOKEN(capsuleId), give me CEK"
   5. Lit verifies on-chain hasAccessByContentId(buyer, capsuleId) → returns CEK
   6. PC2 decrypts blob with CEK
   7. PC2 verifies dev's Ed25519 signature on decrypted bytes
   8. Extract, register, app appears in start menu

Resale flow:
   - Buyer's ACCESS_TOKEN tradable on secondary market via TradeGateway
   - Royalty (e.g. 10%) flows back to creator automatically — no extra plumbing
```

### What's needed to ship Phase 3

| Item | Effort | Touches |
|---|---|---|
| Extend packager: optional encrypt-before-pin path | S (~30 LOC) | New flag in `pc2-node/scripts/package-app.ts` (Phase 1 deliverable) |
| Extend `AppInstallService.install()` to handle `distribution.drm = true` | S (~50 LOC) | Wire to existing `pc2-node/src/api/chipotle-client.ts` for the CEK fetch |
| Creator app: "publish as paid capsule" toggle | S (~1 day UI) | Adds capsuleId minting via existing dDRM contract calls |
| `apps.ela.city`: show prices, route to dDRM buy flow | S (~1 day UI) | Reuses existing Elacity Market buy components |

**Total: ~1 eng-week.** No new contracts. No new infrastructure. Pure composition of two pieces we already have.

### Why this is a Bible §IX (business model) lever

- **Primitive 02 — dDRM protocol fees.** Today: thin margin on every video/PDF licensing transaction. Tomorrow: same margin on every capsule purchase + every capsule resale + every capsule royalty payout. Bible commandment §VII.10 ("Business model impact named") — this lever directly grows the protocol's revenue floor.
- **Primitive 03 — Staking gravity.** Premium capsules (verified, audited, performance-guaranteed) require the publisher to stake N ELA. Stakers in the protocol share in dDRM yield. ELA accrual loop closes.
- **The Four R's all activate at once.** Retain (creators come back to ship more capsules), Review (buyers leave on-chain reviews tied to ownership), Refer (built-in affiliate via the dDRM resale royalty mechanism), Resell (the secondary market is the resale primitive). One feature ships all four R's.

### Why this is the right unification

- Today, "dapp store" and "media marketplace" feel like different products. They aren't — they're the same content-licensing protocol with different content types.
- Every Elacity creator who can sell a video can ship a capsule. **No new mental model. No new payment integration. No new wallet flow.**
- Every dev who builds a capsule can monetize it on day one with the same price/royalty/resale terms they'd set for media.
- Buyers don't need a "wait, this is software, why does it have an ACCESS_TOKEN" explainer — they already understand "I bought a thing, I own the right to use it, I can resell."

### Recommendation

**Phase 1 → Phase 3 is the right sequencing.** Ship free capsules first (Phase 1 + 2) so the install/distribution mechanics are battle-tested. Then layer dDRM (Phase 3) once the registry, signatures, and CIDs all flow correctly. Don't combine them in one release — debugging a flow that's "encrypted AND signed AND on-chain-gated AND IPFS-fetched AND signature-verified" all at once, on the first run, is asking for it.

```

## Capsule formats and the developer experience

> "Do creators need to learn Rust? What's the actual flow to build and ship a capsule?"
>
> Short answer: **no Rust required**. Most capsules are React/Next/Svelte web apps. WASM is for the protocol layer, written and maintained by Elacity Labs.

### The three capsule formats (Anders' Runtime supports all three)

| Format | What it is | When to use it | Source language | Sandbox strength |
|---|---|---|---|---|
| **Web** (iframe today, WebView in Runtime) | HTML + CSS + JS, runs in a browser engine | **99% of capsules with a UI** — storefronts, dashboards, players, viewers, dapps | TS / JS / React / Vue / Svelte | Strong (Chromium sandbox + capability gates) |
| **WASM** (`wasm32-wasip1`) | Compiled binary, deterministic, runs on Wasmtime | Provider capsules + computational kernels — DRM decrypt, IPFS, crypto, model inference, anything performance-critical | Rust (canonical), Go, C++, Zig, AssemblyScript | Strongest (capability-secured, no syscalls without explicit grant) |
| **microVM** (Firecracker) | Full Linux userspace in a hypervisor | Heavy compute that needs a full OS — GPU inference, video transcoding, headless browsers | Anything Linux runs | Strongest, heaviest |
| **data** | Static signed bundle, no execution | Signed configs, registries, content packs | n/a | n/a |

### What this means for creators

- **Default format = Web.** A creator wanting to sell a course, ship a dashboard, gate a Discord, or build the next Glide writes the same React/Next they already write. We package it. They publish. Done.
- **WASM is for the protocol layer.** Our 8 existing crates (`ddrm-renderer`, `aes-gcm-decrypt`, `cenc-decrypt`, `ipfs-assemble`, `mp4-split`, `evm-multicall`, etc.) are WASM. They're consumed *by* capsules, not written *as* capsules by ordinary creators. Same shape as no Steam dev writes Vulkan drivers.
- **microVM is the escape hatch.** Almost no Tier 1 creator needs it. Light it up later for AI/GPU workloads.

**The default Elacity creator picks "web," ships a React app, and never reads this section again.**

### The 10-minute capsule — developer flow

This is the contract. From `git clone` to "my capsule is for sale on the network" must fit in under 10 minutes. Four commands.

```bash
# 1. Scaffold (15 seconds)
npx @elacity/create-capsule storefront my-course
# → creates ./my-course/ with: app.json, index.html, React boilerplate,
#   wallet bridge wiring, dDRM mint button, sample license terms

# 2. Develop (as long as they want)
cd my-course && npm run dev
# → spins up local PC2 in dev mode, opens the capsule, hot reload

# 3. Pack (30 seconds)
elastos capsule pack
# → tarballs the dir, signs with the dev's auto-generated Ed25519 key
#   (kept in ~/.elastos/keys/, encrypted), pins to local IPFS,
#   optionally pushes to apps.ela.city pin service
# → outputs CID + signature + size

# 4. Publish (1 wallet tx)
elastos capsule publish --price 5ela --royalty 10%
# → mints dDRM ACCESS_TOKEN on Base
# → submits registry entry to apps.ela.city
# → returns the listing URL + the elastos://<cid> install URL
```

**Four commands. Four minutes of compute. However much creative time the creator wants in step 2.**

For free capsules: drop `--price` in step 4 and skip the dDRM mint. Same flow.

For updates: edit, `pack`, `publish --update`. Same key signs the new version. Existing buyers get an update prompt.

### Capsule SDK as MCP — vibecoding for sovereign software

> The biggest leverage move for the Acquire (devs) node of the loop. Tracked above as §T1.6.

Wrap the capsule CLI as an MCP server (`@elacity/mcp-capsule-sdk`). Any LLM-driven dev tool — Cursor, Claude Desktop, Continue.dev, Windsurf — can build, sign, publish, and install capsules in natural language.

**The unlock:** every Cursor user (millions, growing) becomes a potential Elacity capsule developer with zero learning curve. The user types *"build me a paid YouTube alternative where viewers pay $0.10/video, creators keep 95%"*; Cursor uses the MCP, scaffolds from `live-stream`, wires the dDRM at $0.10 with `royaltyBps=500`, packs, signs, publishes. **Capsule live on the network in 90 seconds.**

This is **agentic-dev (Bible §X) applied to capsule creation.** The Galaxy delta is public proof; this is the same pattern repeated for every dev.

### The endgame — vibecoding inside ElastOS itself

The Tier 3 / convergence-era version, straight from Rong's "Code Browser" thesis (Bible §I "Data Browser → Code Browser"):

- An **agent capsule** runs on PC2 (already shipping; Anders' README mentions "agent capsule with signed gossip and verified-only AI responses")

**The runtime hosts the IDE that creates capsules for the runtime. Closed loop. Sovereign development.**

Cursor + GitHub + Vercel does this for SaaS today and takes a margin at every step. We do it on PC2, end-to-end on user-owned compute, and the protocol takes <5%. **This is the Bible §VI flywheel running entirely inside three capsules.**

Tier 3 by calendar; Tier 1 by design intent. Every primitive (CLI, MCP, templates, dDRM hooks) is built with the agent-driven case as a first-class user, not an afterthought.
